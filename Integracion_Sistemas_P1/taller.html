4 Anatomía de un endpoint

Regla mental🧱 Recurso en la URI + 🎯 intención en el método. Nunca verbos en la URL.
GET consultar POST crear PUT reemplazar completo PATCH modificar parcial DELETE eliminar
POST /orders
  • 🎯 Crea un pedido
  • 📥 Body: customerId, items[]
  • ✅ 201 Created
  • ❌ 400 · 422 · 500
GET /orders/{orderId}
  • 🧷 Path parameter: identifica el recurso
  • ✅ 200 OK
  • ❌ 404 · 500
GET /orders?customerId=C-1024
  • 🔎 Query parameter: filtra la búsqueda
  • ✅ 200 OK
  • ❌ 400 · 500
PATCH /orders/{orderId}
  • ✏️ Cambia solo algunos campos
  • 📥 Body: status
  • ✅ 200 OK
  • ❌ 404 · 409 · 422

📥 Request (ejemplo del PDF)

POST /orders
{
  "customerId": "C-1024",
  "items": [
    { "productId": "P-500",
      "quantity": 2 }
  ]
}

📤 Response (ejemplo del PDF)

201 Created
{
  "id": "O-9831",
  "customerId": "C-1024",
  "status": "CREATED",
  "total": 129.90
}
🟢

Éxito

200 OK · 201 Created · 204 No Content

Resultado exitoso según el tipo de operación
🟠

Error del consumidor

400 · 404 · 409 · 422

Solicitud inválida, recurso inexistente o conflicto de negocio
🔴

Error del proveedor

500 Internal Server Error

Falla inesperada del servicio

📏 Mínimo por operación: 1 respuesta exitosa + 2 escenarios de error. No uses códigos de forma arbitraria.

🚨 Modelo de error común

{
  "code": "PRODUCT_NOT_AVAILABLE",      ← para máquinas (obligatorio)
  "message": "Product P-500 does not have sufficient stock",  ← para personas (obligatorio)
  "correlationId": "ab23f8b1-91c2-45dc"  ← para rastrear (buena práctica)
}

10 Errores que debes evitar

  

    
❌ /createOrder · /getOrder · /deleteOrder
✅ POST /orders · GET /orders/{id} · DELETE /orders/{id}

    
❌ /executeSPCreateOrder · /database/orders
✅ Nombres del dominio, sin detalles internos

    
❌ Siempre 200 OK, sin importar el resultado
✅ 201, 404, 422, 500 según lo que ocurrió

    
❌ {"error": true}
✅ {code, message, correlationId}

    
❌ Duplicar el mismo schema en cada endpoint
✅ components/schemas + $ref

    
❌ Escribir primero el código y «inventar» después la documentación
✅ Contract First: contrato → validación → código

💡 Ejemplo de decisión de diseño justificada Complemento
    
Decisión: usar PATCH /orders/{orderId} para cancelar en vez de DELETE.
Justificación: el pedido no se borra, solo cambia de estado; así se conserva el historial y el consumidor ve el nuevo status en la respuesta.


  
12 Pregunta de reflexión final

  
Pregunta (sección 23 del PDF)¿Qué ventaja obtiene el sistema consumidor al disponer de un contrato OpenAPI antes de que el proveedor haya terminado de implementar la API?

  
Ver respuesta modelo Complemento

    
  • 🧪 Puede construir y probar su integración en paralelo, con mocks y Postman, sin esperar al backend.
  • 🔍 Detecta ambigüedades del diseño temprano, cuando corregir es barato.
  • 🤖 Puede generar clientes y validar su código contra el contrato.
  • 📅 Depende menos del cronograma del proveedor.

    Debe demostrar comprensión; no basta repetir una definición.

  

    
👀 El consumidor necesita conocer
Endpoints · métodos · parámetros · request/response · códigos de estado · modelo de error

    
🙈 Puede ignorar por completo
Base de datos · lenguaje · stored procedures · servidores · algoritmos internos

  

  
Criterio fundamental del taller: dos sistemas colaboran sin conocer los detalles internos del otro.
