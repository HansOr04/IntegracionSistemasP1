5.3 Resolución modelo: caso e-commerce Complemento

    
Un e-commerce debe integrar (1) la app móvil de clientes, (2) el sistema interno de inventario y (3) una plataforma externa de pagos. Elegir REST, GraphQL o gRPC (y webhook donde aplique) para cada uno.

    
IntegraciónElecciónJustificaciónTrade-off

      
App móvil ↔ backendGraphQL (alternativa: REST con un BFF)Cada pantalla combina perfil, pedidos y recomendaciones; con GraphQL la app pide solo los campos necesarios en una llamada y ahorra datos y latencia móvil. El esquema evoluciona sin versionar.Caché más difícil, control de costo de consultas, curva de aprendizaje. Si el equipo no la domina, REST con un BFF es una opción segura.

      
Backend ↔ Inventario internogRPCComunicación servicio a servicio con alto volumen de llamadas, baja latencia, contrato tipado (.proto) y streaming para sincronizar stock. No se expone a navegadores.Menos legible y más herramientas específicas. Si el tráfico es bajo, REST también es aceptable. Para cambios de stock a escala conviene añadir eventos.

      
Backend ↔ Plataforma de pagos externaREST, más webhook para el resultadoEs un tercero: REST es el estándar universal que ofrecen las pasarelas, simple de integrar y documentado con OpenAPI. Para «pago aprobado» la pasarela notifica por webhook, evitando polling.Hay que usar claves de idempotencia en los POST de pago, verificar la firma del webhook y tolerar reintentos y duplicados.

    
Pre-sesión de clase Del PDF

    
CasoElecciónPor qué

      
A · App móvil: perfil, pedidos y recomendacionesGraphQL (o REST)Vista de datos específica por pantalla y poco ancho de banda.

      
B · Microservicios: miles de llamadas por segundogRPCDesempeño, tipado fuerte y streaming entre servicios.

      
C · Pago aprobado: Stripe debe avisar a nuestro sistemaWebhookNotificación de un evento de un tercero, sin polling.

  


  

    
5.4 Resolución modelo: roleplay Matrícula–Finanzas–CRM Complemento

    
Par de sistemasEstilo recomendadoPor quéTrade-off

      
Matrícula → Finanzas (se matriculó: generar cobro)Messaging (evento MatriculaConfirmada); si Finanzas es legacy sin broker, un File Transfer batch o adaptador como puenteFinanzas puede estar en mantenimiento y Matrícula no debe bloquearse (bajo acoplamiento temporal). Los eventos son confiables y reintentables.Consistencia eventual; hay que manejar duplicados.

      
Matrícula ↔ Finanzas (¿tiene deuda? bloquea la matrícula)Invocación remota síncrona (API REST)Se necesita la respuesta ahora para decidir.Acoplamiento temporal: define timeout y plan B.

      
Finanzas → Matrícula (pago registrado)Messaging (PagoRegistrado)Matrícula reacciona cuando le llega; se desacoplan los ritmos.Retraso de segundos o minutos.

      
Matrícula/Finanzas → CRMMessaging pub/sub; opcionalmente File Transfer nocturno para segmentacionesCRM solo consume (lectura) y tolera consistencia eventual; añadir consumidores no afecta a los productores.El CRM puede ir unos minutos atrás.

      
Los tres sistemas entre síEvitar Shared DatabaseTienen dueños, ritmos y modelos distintos; un cambio de tabla rompería a los demás.Aceptar duplicar datos a cambio de autonomía.
