Semana 2

Patrones clásicos de integración

Objetivos de aprendizaje
  • Describir los cuatro estilos de integración de Hohpe y Woolf.
  • Evaluarlos con criterios: acoplamiento, latencia, formato de datos, confiabilidad, escalabilidad, complejidad.
  • Reconocer sus debilidades y su rol en escenarios legacy.
  • Conocer Apache Camel y WSO2 y aplicar el razonamiento al caso Matrícula–Finanzas–CRM.
Idea central: los primeros estilos resuelven el intercambio de datos, pero cada uno impone un acoplamiento distinto (formato, esquema, disponibilidad) que hay que conocer para elegir.

2.1 Criterios de decisión Complemento

CriterioPregunta que responde
Acoplamiento (coupling)¿Cuánto sabe un sistema del otro? ¿Qué cambio lo rompe?
Oportunidad / latencia (timeliness)¿Qué tan rápido llega un cambio al otro sistema?
Formato de datos¿Qué estructura y qué convención se comparten?
Confiabilidad (reliability)¿Qué pasa si el otro sistema o la red falla?
Escalabilidad (scalability)¿Aguanta más volumen o más participantes?
Complejidad¿Cuánta infraestructura y diseño exige?
Consistencia¿Se requiere ver el mismo dato a la vez en ambos sistemas?
Clave para el examenNo existe un «mejor» estilo universal. La respuesta correcta nombra el criterio dominante del escenario y justifica el compromiso (trade-off).

2.2 Transferencia de archivos (File Transfer) Del PDF Complemento

Definición. Una aplicación produce un archivo con los datos que otra necesita y esta lo consume más tarde. Es el estilo más antiguo y universal.

El archivo también tenía un contrato. Del PDF Aunque no se declare, el intercambio por archivos define acuerdos implícitos:

ElementoImplicación arquitectónica
CSV / XMLContrato de estructura de datos
Ruta / FTP / SFTPContrato de ubicación y acceso
Batch / horarioContrato temporal
Nombre de archivoConvención compartida
Logs / archivo de errorRetroalimentación diferida: baja dependencia temporal, mayor latencia
El archivo es el contrato entre ambos sistemas.

Idea clave (diapositiva). Del PDF No es un estilo «malo»: es apropiado cuando el contexto tolera procesamiento por lotes.

Ejemplo. Finanzas exporta cada noche pagos_20261025.csv a una carpeta SFTP y Matrícula lo importa a las 6:00.

Ventajas
  • Muy simple; no exige APIs
  • Bajo acoplamiento temporal
  • Funciona con sistemas legacy
  • Los archivos sirven de evidencia y auditoría
Desventajas
  • Latencia alta, datos desactualizados
  • Archivos parciales, bloqueos, duplicados
  • Formato libre, validación manual
  • Retroalimentación de errores diferida
Cuándo usarlo
  • Cargas nocturnas, conciliaciones, intercambio con terceros
  • Sistema legacy que solo exporta archivos
Cuándo no
  • Cuando otro sistema necesita el dato «ahora»

Pregunta de transición (diapositiva). Del PDF «¿Y si Inventario necesita el pedido ahora?». Hay que decidir si se sigue esperando un CSV o se expone una capacidad: de ahí nace la API.

Defensa del taller de archivos Del PDF

Por grupo, 5 a 7 minutos: demostración funcional antes que explicación teórica; ejecutar con un archivo de entrada real; mostrar entrada, validación, transformación y salida; evidenciar registros válidos, inválidos y errores; explicar las decisiones de arquitectura. Se evalúa la comprensión de los puntos de acoplamiento, las decisiones de integración y el tratamiento de errores. Consigna: muestren evidencia, no solo código.

2.3 Base de datos compartida (Shared Database) Complemento

Definición. Varias aplicaciones leen y escriben en una misma base de datos con un esquema común, que actúa como punto de integración.

Todos dependen del mismo esquema.

Cómo funciona. El esquema unificado se diseña para todos. Las transacciones ACID mantienen la consistencia: lo que escribe una aplicación se ve de inmediato.

Ventajas
  • Datos siempre consistentes y actuales
  • Sin duplicación ni sincronización
  • Transacciones ACID
Desventajas
  • Acoplamiento fuerte al esquema: cambiar una tabla puede romper a todos
  • Cada app tiene necesidades distintas; el modelo único es un compromiso difícil
  • Contención, bloqueos y cuello de botella
  • No funciona entre organizaciones o sistemas empaquetados
Cuándo usarlo
  • Aplicaciones de un mismo equipo y dominio que exigen consistencia fuerte
Cuándo no
  • Sistemas con dueños distintos, productos de terceros o necesidad de evolucionar de forma independiente

2.4 Invocación remota de procedimientos (RPC / Remote Procedure Invocation) Complemento

Definición. Una aplicación expone una funcionalidad como procedimiento que otra invoca de forma remota, como si fuera una llamada local. Ejemplos: CORBA, Java RMI, DCOM, SOAP/RPC, gRPC.

Cómo funciona. El cliente llama a un stub generado a partir de una interfaz (IDL); el stub serializa los parámetros y los envía por la red; el skeleton del servidor los deserializa, ejecuta y devuelve el resultado.

RPC: llamada síncrona con respuesta inmediata.
Ventajas
  • Encapsula datos y lógica: el cliente no ve el modelo interno
  • Respuesta inmediata
  • Modelo mental familiar
Desventajas
  • Acoplamiento temporal: si el servidor falla, el cliente falla
  • Ilusión de «llamada local» que oculta latencia y fallos de red
  • Acoplamiento a la firma del procedimiento
Error comúnTratar una llamada remota como local. Ignora las falacias de la computación distribuida (la red es confiable, la latencia es cero...). Una llamada remota puede fallar, tardar o ejecutarse dos veces.

2.5 Mensajería (Messaging): el cuarto estilo de EIP Complemento

Definición. Las aplicaciones intercambian paquetes de datos pequeños y frecuentes llamados mensajes, a través de un canal gestionado por un sistema de mensajería (message broker).

Cómo funciona. El productor envía y continúa; el canal guarda el mensaje (store-and-forward) hasta que el consumidor está disponible. Existen colas (punto a punto) y tópicos (publish/subscribe). Además, reintentos, colas de mensajes fallidos (dead letter queue, DLQ) y garantías de entrega.

El canal desacopla en el tiempo al productor y al consumidor.
Ventajas
  • Bajo acoplamiento temporal y de ubicación
  • Alta confiabilidad y buena escalabilidad
  • Latencia baja, procesamiento asíncrono
Desventajas
  • Requiere infraestructura (broker)
  • Complejidad: orden, duplicados, consistencia eventual
  • Depuración más difícil

Es la base conceptual de EAI y EDA, y el estilo en el que se organiza el catálogo de patrones de EIP (canales, enrutadores, transformadores, endpoints).

2.6 Herramientas: Apache Camel y WSO2 Complemento

Apache Camel (overview). Framework de integración de código abierto que implementa los patrones EIP. Conceptos: ruta (route), endpoint (identificado por URI), componente (component), procesador (processor), intercambio (exchange) y contexto (CamelContext). Se configura con un DSL en Java, XML o YAML.

from("file:data/entrada?noop=true")      // endpoint origen: carpeta
    .unmarshal().csv()                    // transforma CSV a objetos
    .filter(simple("${body[estado]} == 'PAGADO'"))
    .marshal().json()                     // transforma a JSON
    .to("http://localhost:8080/pagos");   // endpoint destino: API

WSO2 Integration Studio / Enterprise Integrator (taller de transferencia de archivos). Integration Studio es el IDE con el que se diseñan artefactos de integración que se ejecutan en el Micro Integrator. En el taller se implementa un flujo de File Transfer: leer archivos de una carpeta de entrada (transporte VFS o conector de archivos), validar y transformar, y escribir una salida más un archivo de errores.

IdeaCamel y WSO2 muestran que los patrones son el vocabulario y las herramientas son la implementación: el mismo patrón se ve en ambos.

2.8 Limitaciones y rol en escenarios legacy Complemento

  • File Transfer: latencia y fragilidad operativa; útil como puente con sistemas legacy sin interfaces modernas.
  • Shared Database: acoplamiento al esquema; evitarla entre sistemas con dueños distintos.
  • RPC: acoplamiento temporal y a la firma; el origen del movimiento hacia interfaces explícitas (APIs).
  • Messaging: el más flexible, pero con mayor complejidad.
Clave para el examenLos enfoques tradicionales no «desaparecen»: en un entorno legacy suelen ser la única opción realista y conviven con APIs y eventos.
