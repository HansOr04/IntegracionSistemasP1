Semana 3

APIs como estándar de integración

Objetivos de aprendizaje
  • Explicar por qué una API es un contrato de integración y no solo una URL.
  • Modelar recursos, URIs y métodos HTTP con criterios REST; razonar con idempotencia y códigos de estado.
  • Formalizar el contrato con OpenAPI y probarlo en Postman (enfoque Contract First).
  • Elegir entre REST, GraphQL, gRPC y webhooks según la interacción.
Idea central: una API es la frontera estable entre dos sistemas; el consumidor depende del contrato, no de la implementación interna.

3.1 Una API es una frontera, no solo una URL Del PDF

Definición. Una API (Application Programming Interface) es la interfaz mediante la cual un software expone capacidades o información a otro. Analogía de clase: como en un restaurante, el cliente conoce el menú y no la cocina.

Del archivo a la API. La API sustituye el intercambio diferido por archivos por una interacción inmediata regida por un contrato explícito. Equivalencias de la diapositiva:

Clave para el examenEl consumidor depende del contrato, no de la implementación interna. Un buen contrato evita acuerdos informales y acoplamiento accidental. Criterio fundamental del taller: ¿qué necesita conocer el consumidor y qué puede ignorar del proveedor?

3.2 Evolución: SOAP → REST → GraphQL y gRPC (más webhooks) Del PDF Complemento

  • SOAP (Simple Object Access Protocol, ~1998): mensajes XML en un envelope, contrato WSDL, estándares WS-*. Robusto, pero verboso.
  • REST (Representational State Transfer, tesis de Fielding, 2000): recursos sobre HTTP, representaciones JSON. Se populariza hacia 2010 por su simplicidad.
  • GraphQL (Facebook, publicado en 2015): el cliente especifica exactamente los campos que necesita en un único endpoint.
  • gRPC (Google, 2015): RPC moderno con Protocol Buffers sobre HTTP/2, con streaming.
  • Webhook: el proveedor llama a una URL del consumidor cuando ocurre un evento. Del PDF

Cuatro mecanismos, cuatro tipos de interacción Del PDF

Ideal paraFortalezaTrade-off
RESTAPIs públicas y ecosistemas heterogéneosInteroperabilidad y tooling webPuede sobre o subobtener datos
GraphQLClientes con vistas de datos diferentesEl cliente pide exactamente lo necesarioGobernanza, caching y costo de consultas
gRPCComunicación intensa entre serviciosContrato tipado, streaming y eficienciaMenos natural para navegador directo
WebhookNotificar a un tercero cuando ocurre un eventoEvita polling constanteSeguridad, retries, duplicados e idempotencia

No son reemplazos universales; pueden coexistir en una misma solución. Hay que elegir por interacción, no por moda.

Error comúnCreer que GraphQL o gRPC «reemplazan» a REST. Cada uno resuelve una interacción distinta. Y un webhook no es una API que se consulta: es una notificación que el proveedor inicia.

3.3 Principios REST y diseño de recursos Del PDF Complemento

Idea central. REST no es solo «usar GET/POST». El cambio mental es modelar recursos y representaciones: la URI identifica el recurso y el método HTTP expresa la intención. Del PDF

Evitar: acciones en la URL

  • /createOrder
  • /getOrder
  • /updateOrder
  • /executeSPCreateOrder
  • /database/orders

Preferir: recursos

  • POST /orders
  • GET /orders/{orderId}
  • PATCH /orders/{orderId}
  • GET /orders?customerId=C-1024

Restricciones de REST (Fielding). Cliente-servidor, sin estado (stateless), caché (cacheable), interfaz uniforme (uniform interface), sistema en capas (layered) y código bajo demanda (opcional). La interfaz uniforme incluye identificación de recursos, manipulación mediante representaciones, mensajes autodescriptivos e hipermedia (HATEOAS).

Reglas prácticas de URIs. Sustantivos en plural (/orders), jerarquía solo cuando expresa pertenencia (/customers/{id}/orders), minúsculas y guiones, sin verbos ni extensiones, sin exceso de anidación (como regla práctica, no más de colección/elemento/colección).

Pregunta de clase. Del PDF ¿GET /orders?customerId=123 o GET /customers/123/orders? Ambas pueden ser válidas: la primera trata los pedidos como una colección filtrable (más flexible para filtros combinados); la segunda expresa la pertenencia y facilita la navegación. Se justifica por semántica, navegación y evolución.

Modelo de madurez de Richardson. Nivel 0: un endpoint y un verbo (pantano POX). Nivel 1: recursos. Nivel 2: verbos HTTP y códigos de estado correctos. Nivel 3: hipermedia (HATEOAS). La mayoría de las APIs «REST» reales se quedan en el nivel 2.

3.4 Métodos HTTP, seguridad e idempotencia Del PDF

No se memorizan verbos: se elige una semántica observable para el consumidor. Regla mental: recurso en la URI + intención en el método.

IntenciónMétodoEjemplo
ListarGET/orders
ConsultarGET/orders/{id}
CrearPOST/orders
Reemplazar / modificarPUT / PATCH/orders/{id}
EliminarDELETE/orders/{id}

Reintentos: ¿qué pasa si repito la solicitud?

Safe (seguro): no debería cambiar el estado del servidor. Idempotente (idempotent): repetirla produce el mismo estado final. GET es seguro e idempotente. PUT y DELETE son idempotentes. POST normalmente no lo es. Importa porque la red puede fallar después de enviar una operación: el cliente no sabe si el servidor la procesó y reintenta.

Ejemplo de idempotenciaSi PUT /orders/O-1 con estado «CANCELADO» se repite diez veces, el pedido sigue cancelado. Si POST /orders se repite diez veces, podría crear diez pedidos. Solución habitual: una clave de idempotencia (Idempotency-Key) en el header para que el servidor reconozca el reintento.

PUT frente a PATCH. PUT reemplaza el recurso completo con la representación enviada. PATCH modifica parcialmente y no está garantizado como idempotente (depende de cómo se defina).

Error comúnUsar POST para todo, o GET para operaciones que cambian estado. Los intermediarios (cachés, proxies, rastreadores) asumen que GET no tiene efectos secundarios.

3.5 Request, response, códigos de estado y errores Del PDF

Request y response son un contrato observable. Ejemplo (del PDF):

POST /orders
Content-Type: application/json

{ "customerId": "C-1024", "items": [ { "productId": "P-500", "quantity": 2 } ] }

HTTP/1.1 201 Created
Location: /orders/O-9831

{ "id": "O-9831", "customerId": "C-1024", "status": "CREATED", "total": 129.90 }
  • Método + endpoint: operación y recurso.
  • Headers: metadatos, formato y control.
  • Parámetros y body: datos de entrada.
  • Status code: resultado semántico (201 expresa más que un 200 genérico).
  • Response body: representación resultante.

Éxitos y errores también se diseñan

{ "code": "PRODUCT_NOT_AVAILABLE",
  "message": "Product P-500 does not have sufficient stock",
  "correlationId": "ab23f8b1-91c2-45dc" }

El modelo de error debe tener como mínimo code y message; el correlationId es una buena práctica que permite rastrear la petición entre sistemas. Conviene separar el error técnico, el error de negocio y el mensaje para quien integra. Complemento El estándar RFC 9457 (Problem Details, application/problem+json) formaliza este tipo de modelo.

Tipos de respuesta. Éxito: 200 OK, 201 Created, 204 No Content. Error del consumidor: 400, 404, 409, 422. Error del proveedor: 500. Los códigos no se usan arbitrariamente: el status debe representar el resultado de la operación.

Errores que evitar (taller)Responder siempre 200 OK sin importar el resultado; devolver errores ambiguos como {"error": true}; duplicar schemas en cada operación; escribir primero el código para luego «inventar» la documentación.

3.6 Parámetros, paginación, filtrado y versionado Del PDF Complemento

Path parameter: identifica un recurso específico o parte esencial de la ruta (GET /orders/{orderId}). Query parameter: filtra, ordena, busca o modifica una consulta (GET /orders?customerId=C-1024). Del PDF

  • Paginación (pagination) Complemento: por desplazamiento (?limit=20&offset=40) o por cursor (?cursor=abc123), más estable cuando los datos cambian. Se suelen devolver enlaces y el total.
  • Filtrado y orden: ?status=CREATED&sort=-createdAt.
  • Versionado (versioning): en la URI (/v1/orders), en un header (Accept: application/vnd.acme.v1+json) o en un query parameter. Sirve para cambios incompatibles.
  • HATEOAS (Hypermedia As The Engine Of Application State): la respuesta incluye enlaces a las acciones posibles (_links: { self, cancel, payment }), de modo que el cliente navega sin hardcodear URIs.

Compatibilidad: un contrato debe poder evolucionar Del PDF

Compatible
Agregar un campo opcional ("priority": "NORMAL") suele preservar a los consumidores existentes.
Incompatible
Renombrar o eliminar un campo (customerId → clientId) rompe integraciones.

Versionar ayuda, pero no sustituye diseñar y comunicar la compatibilidad. Un consumidor debe tolerar campos nuevos que no conoce.

3.7 OpenAPI: el contrato hecho explícito Del PDF Complemento

Definición. OpenAPI es un estándar para describir APIs HTTP en YAML o JSON. Describe la interfaz; no implementa la lógica de negocio. (Antes se llamaba Swagger; hoy lo mantiene la OpenAPI Initiative y Swagger UI, Editor y Codegen son herramientas del ecosistema.)

Estructura.

  • openapi: versión de la especificación (por ejemplo 3.0.3).
  • info: título, versión y descripción.
  • servers: URLs base.
  • paths: endpoints y operaciones (parameters, requestBody, responses).
  • components: elementos reutilizables (schemas, parameters, responses, securitySchemes).

Para qué sirve. Documentación, mocks, SDKs generados, pruebas e implementación guiada por el contrato. Los modelos principales se declaran en components/schemas y se reutilizan con $ref; la especificación debe incluir ejemplos de request y response.

Ver un contrato completo y comentado en Práctica de API.

3.8 Contract First y el taller de la Orders API Del PDF

Enfoque Contract First: necesidad de negocio → contrato → validación → implementación. No se escribe primero el código para luego «inventar» la documentación.

1 Comprender el problema→2 Identificar sistemas→3 Identificar recursos→4 Diseñar operaciones→5 Request/response→6 Errores→7 Formalizar en OpenAPI→8 Validar→9 Importar en Postman

Del problema al contrato (resumen de la clase). Problema → interacción → mecanismo → contrato → especificación → implementación.

Qué pide el taller

  • Dominio a elegir: pedidos, matrículas, citas médicas, pagos o inventario.
  • Contexto: sistema proveedor, sistema consumidor, propósito (máximo cinco líneas) y recursos principales.
  • Alcance mínimo: 3 endpoints, 2 métodos HTTP diferentes, 1 path parameter, 1 query parameter, 1 request body, schemas reutilizables, respuestas exitosas, al menos 2 escenarios de error, modelo común de error, ejemplos de request y response, OpenAPI válido, colección Postman con 3 requests y README con decisiones de diseño.
  • Fuera de alcance: OAuth2, JWT, API Gateway, rate limiting, Service Mesh, observabilidad distribuida, Kubernetes, microservicios completos, base de datos y backend funcional.
  • Entregables: carpeta con openapi.yaml (o json), README.md y postman/API.postman_collection.json.
  • README: nombre de la API, problema de integración, sistemas, recursos, tabla de endpoints, al menos tres decisiones de diseño justificadas y respuesta a la pregunta de reflexión.

Postman sin backend

Se importa el OpenAPI, se genera la colección, se configura la variable de base URL y se revisan al menos tres requests (POST /orders, GET /orders/{orderId}, GET /orders?customerId=C-1024). Sin backend, Postman demuestra métodos, URLs, parámetros, headers, bodies y los ejemplos de respuesta definidos en el contrato. Se evalúa la calidad del diseño, no la implementación. En la clase se añade una revisión cruzada de contratos de 3 minutos: el grupo revisor señala una fortaleza y una mejora concreta.

Pregunta de reflexión del taller¿Qué ventaja obtiene el consumidor al tener un contrato OpenAPI antes de que el proveedor termine la implementación? Respuesta modelo: puede desarrollar y probar su integración en paralelo usando mocks y la colección de Postman, detectar ambigüedades del diseño temprano (cuando corregir es barato), generar clientes y validar su propio código contra el contrato, y reducir la dependencia del cronograma del proveedor.

3.9 GraphQL y gRPC en detalle Complemento

REST: varios endpoints por recurso; la respuesta es lo que el servidor define. Riesgo: over-fetching (recibir de más) y under-fetching (necesitar varias llamadas).

GraphQL: un único endpoint (POST /graphql); el cliente describe el árbol de datos que necesita; el esquema está tipado (SDL) y las consultas se resuelven con resolvers. Evita over/under-fetching. Costos: caché más difícil, riesgo de consultas muy costosas (se limita profundidad o costo), problema N+1 en resolvers.

gRPC: contrato en un archivo .proto, serialización binaria con Protocol Buffers, HTTP/2 (multiplexación) y streaming (unario, servidor, cliente, bidireccional). Muy eficiente entre servicios internos; limitado directamente en navegadores (se usa gRPC-Web).

Webhook. Del PDF El proveedor llama al consumidor cuando ocurre un evento (por ejemplo, una pasarela de pagos avisa «pago aprobado»). Evita polling, pero exige verificar la firma, gestionar reintentos y ser idempotente ante duplicados.
