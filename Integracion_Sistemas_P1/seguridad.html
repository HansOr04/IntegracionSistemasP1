🔐 Seguridad de APIs

Complemento Esta página no viene en los PDFs. Reúne lo que conviene saber para diseñar APIs seguras y para justificar decisiones en el README.

🎯 Idea central: una API expone capacidades de tu sistema; el contrato debe decir también quién puede hacer qué y qué pasa cuando algo falla.

1 Por qué importa

🎯

Superficie de ataque

Cada endpoint es una puerta. Cuanto más expones, más debes proteger.

📜

El contrato también protege

OpenAPI declara el esquema de seguridad y los errores 401, 403 y 429.

⚖️

Alcance del taller

OAuth2, JWT, API Gateway y rate limiting no se implementan en el taller, pero puedes explicar cómo los usarías.

2 Los conceptos base

ConceptoPreguntaSe traduce en

Autorización (authorization)¿Qué puedes hacer?403 si estás autenticado pero sin permiso
Confidencialidad¿Alguien puede leer el tráfico?HTTPS (TLS) siempre

Disponibilidad¿Se puede abusar del servicio?Límite de solicitudes, 429 con Retry-After

1 · Header

Algoritmo y tipo.

{"alg":"HS256","typ":"JWT"}

2 · Payload (claims)

Quién es y qué puede hacer.

{"sub":"C-1024",
 "scope":"orders:read",
 "iss":"auth.miempresa.com",
 "aud":"orders-api",
 "exp":1767225600}

3 · Firma

Garantiza que nadie alteró header ni payload.

Error comúnCreer que un JWT está cifrado. Normalmente solo está firmado: el payload se codifica en Base64URL y cualquiera puede leerlo. No guardes secretos ni datos sensibles dentro.

La API debe validar en cada petición: la firma, la expiración (exp), el emisor (iss), la audiencia (aud) y los permisos (scope).

6 OWASP API Security Top 10 (2023)

Lista de los riesgos más frecuentes en APIs. Conviene reconocer los nombres y la idea de cada uno.

API1 · Broken Object Level Authorization (BOLA)Pedir el recurso de otra persona cambiando el id. Mitiga: comprobar que el objeto pertenece a quien pregunta.
API2 · Broken AuthenticationLogin o tokens débiles. Mitiga: expiración, MFA, protección contra fuerza bruta.
API3 · Broken Object Property Level AuthorizationVer o modificar campos que no te corresponden. Mitiga: filtrar propiedades de entrada y salida.
API4 · Unrestricted Resource ConsumptionSin límites de tamaño o frecuencia. Mitiga: rate limiting, paginación, tope de body.
API5 · Broken Function Level AuthorizationUn usuario normal llama a operaciones de administrador. Mitiga: permisos por operación.
API6 · Unrestricted Access to Sensitive Business FlowsAutomatizar un flujo de negocio (compras masivas). Mitiga: límites y detección de abuso.
API7 · Server Side Request Forgery (SSRF)La API hace peticiones a una URL que controla el atacante. Mitiga: lista de destinos permitidos.
API8 · Security MisconfigurationCORS abierto, errores detallados, configuración por defecto. Mitiga: configuración endurecida y revisada.
API9 · Improper Inventory ManagementVersiones viejas o endpoints olvidados. Mitiga: inventario y retiro de versiones.
API10 · Unsafe Consumption of APIsConfiar a ciegas en datos de otras APIs. Mitiga: validar también lo que recibes de terceros.

7 Ejemplo: el riesgo API1 (BOLA)

❌ Vulnerable
app.get('/orders/:orderId', auth, (req,res) => {
  const order = orders.get(req.params.orderId);
  res.json(order);   // cualquiera con token ve cualquier pedido
});
✅ Correcto
app.get('/orders/:orderId', auth, (req,res) => {
  const order = orders.get(req.params.orderId);
  if (!order) return fail(res,404,'ORDER_NOT_FOUND','...');
  if (order.customerId !== req.user.sub)
    return fail(res,403,'FORBIDDEN','No access to this order');
  res.json(order);
});

Estar autenticado no basta: hay que comprobar de quién es el objeto.

8 Cómo se declara en OpenAPI

Se define el esquema en components/securitySchemes, se aplica con security y se documentan los errores 401, 403 y 429. El archivo completo está en la página Taller: cómo hacer el código (pestaña «openapi + seguridad»).

components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
security:
  - bearerAuth: []          # se aplica a todas las operaciones
paths:
  /orders/{orderId}:
    get:
      responses:
        '200':
          description: Pedido encontrado
        '401':
          $ref: '#/components/responses/Unauthorized'
        '403':
          $ref: '#/components/responses/Forbidden'
        '429':
          $ref: '#/components/responses/TooManyRequests'
ClavePara dejar una operación pública (por ejemplo un catálogo) se escribe security: [] en esa operación.

9 En el código y en Postman

🧩 En el backend

  • HTTPS siempre; el token viaja en Authorization.
  • Comparar tokens con crypto.timingSafeEqual.
  • Limitar el tamaño del body y las solicitudes por minuto.
  • Validar el body contra el schema.
  • Errores sin stack trace; detalle solo en el log.

Ejemplos reales en el server.js opcional.

📮 En Postman

  • Pestaña Authorization → tipo Bearer Token.
  • Guarda el token en una variable ({{token}}), no lo escribas fijo.
  • Usa variables de entorno para secretos.
  • No subas la colección con secretos a un repositorio.
API_TOKEN=secreto123 node server.js curl -i http://localhost:8080/orders # 401 curl -i -H 'Authorization: Bearer secreto123' http://localhost:8080/orders # 200

El token de ejemplo es solo para pruebas locales. En producción lo emite un servidor de autorización y expira.

10 Errores de seguridad típicos

❌ Token o clave en la URL (?token=...)
✅ En la cabecera Authorization (la URL queda en logs e historial)
❌ Mensaje de error con el stack trace
✅ Mensaje genérico + correlationId; detalle solo en el servidor
❌ CORS abierto a cualquier origen con credenciales
✅ Lista de orígenes permitidos
❌ Confiar en que el cliente envía datos correctos
✅ Validar siempre en el servidor
❌ Secretos escritos en el código o en el repositorio
✅ Variables de entorno o un gestor de secretos
❌ HTTP sin cifrar
✅ HTTPS (y HSTS) en producción
